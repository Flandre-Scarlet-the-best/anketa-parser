# Отчёт о трёх этапах отбора

Команда `report html` собирает по существующему хранилищу один автономный
HTML-файл: посты одного снимка источника, решения первичного фильтра и решения
модели по каждому посту. Команда только читает схему продукта, не применяет
миграции и не вызывает модель. Отчёт нужен, чтобы разбирать конкретный прогон
глазами, а не восстанавливать его по логам и отдельным SQL-запросам.

Как появляются сами данные, описано в руководствах по
[Двачу](dvach.md) и [текстовому анализу](llm.md). Здесь объясняется только
чтение их результатов и то, что попадает в файл.

## Что читает отчёт

- `Source` по ключу источника и единственную строку `SourceScan` этого
  источника: границы последнего скана, его статус, фазу, журнал и счётчики.
- `OriginalPost`, у которых `LastSeenAt` попадает в окно
  `[StartedAt, FinishedAt]` скана, их актуальную ревизию (`IngestedRevisionId`)
  и все сохранённые ревизии этих постов.
- Решение фильтра и адресацию в ревизии, число найденных контактов, признак
  неоднозначности, подготовленный текст и признак исключения модерацией у поста.
- Задания обработки и их попытки, решения модели с фрагментами-основаниями и
  связанные наблюдения контактов, а также состояние созданной анкеты.
- Необязательный JSON с метаданными запуска, переданный параметром
  `--run-metadata` (см. [ниже](#метаданные-запуска)).

Посты этого источника, увиденные раньше окна скана, показываются отдельным
блоком и в снимок не входят: их решения и анкеты сохранены, но к этому скану не
относятся. Ограничение блока — 200 постов.

## Доказуемость снимка

Отчёт описывает один зафиксированный набор постов, поэтому смешивать два скана
нельзя. Перед построением документа проверяется, что:

- у скана статус и фаза `complete`, журнал применённых записей пуст;
- известны обе границы окна;
- применено ровно столько записей, сколько получено;
- постов внутри окна ровно столько, сколько получено, и столько же прочитано;
- у каждого поста есть актуальная ревизия и ни одна из них не получена позже
  `FinishedAt`.

Если хотя бы одно условие не выполнено, HTML не пишется: команда возвращает
категорию отказа вместе с фактическими значениями (получено, применено, постов в
окне, границы окна, номера проблемных постов). Возобновлённый скан, у которого
перезаписан `StartedAt`, такой проверкой отклоняется — состав его постов по схеме
недоказуем, и отчёт по нему не строится. Истории сканов в схеме нет: `SourceScan`
описывает только последний скан источника, поэтому отчёт всегда относится именно
к нему.

## Аргументы

| Аргумент | Назначение |
| --- | --- |
| `--output <файл>` | Обязательный путь создаваемого HTML-файла. Каталог создаётся при необходимости. |
| `--source-key <ключ>` | Ключ источника (`Source.Key`). По умолчанию берётся адрес треда из `Dvach:ThreadUrl`. |
| `--run-metadata <файл>` | Необязательный JSON с описанием движка и параметров запуска. |
| `--fixture` | Использовать ключ фикстуры вместо адреса треда. |
| `--json` | Принимается для совместимости: машинный отчёт всегда пишется в stdout. |

Ключ источника не задаётся в коде: он либо передаётся аргументом, либо выводится
из действующей настройки сбора. Справка по команде — `report help`.

## Сформировать и открыть файл

Подключение к PostgreSQL берётся из обычного конвейера конфигурации
([Конфигурация](configuration.md)); учётной роли достаточно прав на чтение схемы
продукта. Если соединение не настроено, команда завершается кодом 3 и файл не
создаёт.

```powershell
dotnet run --project src/AnketaParser.Cli -- report html --output artifacts/report/report.html
Start-Process artifacts/report/report.html
```

Человекочитаемая строка о результате пишется в stderr, машинный JSON — в stdout,
код завершения 0 означает, что файл записан. Файл пишется целиком после успешной
сборки документа, поэтому частичного отчёта не остаётся.

## Что попадает в отчёт

Три разреза показаны раздельно и не сводятся к одному «исключён»:

- решение первичного фильтра — `candidate`, `opening_post`, `no_own_contact`;
- адресация — `op`, `op_reply`, `none`, `other_reply`; чужой ответ не является
  причиной отсева и в причинах отсева не показывается;
- исключение модерацией (`Excluded`) — отдельный признак поста, который не меняет
  решение фильтра.

Этап модели показывает класс решения (`profile`, `not_profile`, `uncertain`) и
состояние задания: ожидает, выполняется, технический отказ, задания нет, пост не
допущен к анализу, есть только устаревшие ревизии, решение без класса. Отсутствие
результата модели никогда не показывается как `not_profile`: отказы вынесены в
отдельный раздел, а статусы посчитаны с явными знаменателями.

Фрагмент-основание хранится координатами UTF-16 и восстанавливается из текста
ревизии. Подсветка выполняется только после проверки: смещения внутри текста,
фрагмент не содержит символа маски, значение поля входит во фрагмент. Иначе
фрагмент показывается без подсветки с причиной.

## Ограничения данных

Отчёт сам перечисляет ограничения, при которых его нужно читать осторожно:

- текст, отправленный модели, и хеш маски в базе не сохраняются, поэтому блок
  «подготовленный текст» — реконструкция по текущим наблюдениям контактов;
- в схеме нет хеша файла модели, параметров сэмплинга, endpoint и имени профиля:
  такие сведения попадают в отчёт только из метаданных запуска;
- истории сканов нет, поэтому снимок строится по границам последнего скана;
- при неподтверждённых координатах и нереконструированной маске появляются
  предупреждения с числом затронутых постов.

## Метаданные запуска

`--run-metadata` принимает произвольный JSON: схема файла не фиксирована. Команда
ищет известные сведения по именам полей (модель, движок, версия движка,
квантование, SHA-256, endpoint, параметры запуска) и рядом показывает полный
список плоских значений с их путями, чтобы источник каждого факта был виден.
Строки сокращаются до 300 символов, число значений ограничено.

Файл необязателен. Без него отчёт строится по сохранённым решениям модели и прямо
сообщает, что метаданные запуска не переданы. Секреты и токены в этот JSON класть
нельзя: его значения попадают в отчёт как есть.

## Автономность файла

После генерации отчёт не требует сети, базы данных и модели. Это один файл:
стили и скрипты встроены, CSP-заголовок с хешами собран из них же, внешних
таблиц стилей, скриптов, шрифтов, изображений и фреймов нет. Фильтры, поиск и
раскрытие подробностей работают локально в браузере, поэтому файл можно открыть
двойным щелчком или передать коллеге без сервера.

## Персональные данные и публикация

Отчёт содержит авторские тексты постов, цитаты, адреса и распознанные контакты в
исходном и нормализованном виде, а также подробности конкретного прогона
(модель, версии, время, счётчики). Это персональные данные третьих лиц, поэтому
сгенерированный файл не публикуется в Git: его сохраняют в исключённый из
репозитория каталог (например, `artifacts/`) и не прикладывают к PR, задачам и
переписке. В репозиторий попадают только команда, её тесты и эта инструкция.

## Коды завершения

| Код | Значение для `report html` |
| --- | --- |
| 0 | Отчёт построен, HTML записан. |
| 2 | Неверные аргументы: неизвестная операция, лишний параметр, нет `--output`. |
| 3 | Конфигурация или входные данные: не настроено хранилище, не задан ключ источника, нечитаемые или некорректные метаданные запуска, недоступный путь вывода. |
| 4 | Снимок недоказуем, схема продукта отсутствует или хранилище недоступно. |
| 1 | Непредвиденная внутренняя ошибка или отмена. |

Общий контракт кодов и машинного вывода описан в разделе
[CLI и готовность](diagnostics.md).
