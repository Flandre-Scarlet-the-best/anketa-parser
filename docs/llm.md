# Текстовый анализ сообщений

Сборщик ставит актуальные ревизии с собственным контактом в PostgreSQL.
Отдельный процесс Worker читает авторский текст, скрывает распознанные
контакты и ссылки, затем запрашивает классификацию. Только для класса
`profile` он запрашивает извлечение полей. Доказательства привязаны
к смещениям UTF-16 в подготовленном тексте ревизии.
Поля без проверяемого фрагмента опускаются. В анализе сохраняются
имена отклонённых полей, но не имена полей, для которых модель вернула `null`.
Англоязычные инструкции требуют копировать значение и фрагмент без перевода.
Словарная подпись показывается отдельно от исходного написания: например,
«Кун, 26» даёт «Парень», а «живу в ДС-1» — «Москва». «Ищу тян» не
подтверждает пол автора, а «дс» без цифры не является обозначением города.

| Решение | Что сохраняется |
| --- | --- |
| `profile` | Решение, подтверждённые поля и анкета в состоянии `Candidate` |
| `not_profile` | Решение об явно постороннем сообщении и его основание |
| `uncertain` | Решение о неоднозначности, контакте без описания или нехватке контекста |

Возраст, пол, город, интересы и остальные поля могут отсутствовать.
Неполный вывод, ошибка формата, таймаут и другие технические отказы
отражаются в попытках задания. Формирование анкеты не меняет её
модерацию, привязки, подтверждение контакта и публикацию.

## Выбрать профиль

Скопируйте [llm.example.toml](../llm.example.toml) в приватный `llm.toml`.
Запускайте CLI из корня проекта. Пустой `active_profile` и отсутствие
необязательного файла дают статус `disabled`. Для опубликованного
артефакта или запуска из другого каталога задайте
`ANKETAPARSER_Llm__ConfigPath`. Относительные пути к моделям считаются
от каталога TOML. Путь и активный профиль можно задать в общей
конфигурации приложения через `Llm:ConfigPath` и `Llm:ActiveProfile`.
Переменные `ANKETAPARSER_Llm__ConfigPath` и
`ANKETAPARSER_Llm__ActiveProfile` имеют обычный приоритет окружения.
Данные профилей читаются из TOML при запуске.

| Движок | Настройка |
| --- | --- |
| `openai` | Укажите базовый URL API с нужным префиксом, ID модели и, если требуется, `key_env`. Клиент добавляет `/chat/completions`. Для удалённого маршрута нужен HTTPS, HTTP допускается на loopback. |
| `llama_server` | Укажите адрес и модель своего `llama-server`. Режим `llama_schema` передаёт схему в формате `response_format.type=json_object` и `response_format.schema`. |
| `native` | Укажите совместимый GGUF, размер контекста, число потоков и слои GPU. Модель загружается один раз на процесс. CPU поставляется с CLI. Для offload требуется совместимый нативный CUDA или Vulkan backend той же версии LLamaSharp и его системные зависимости. |

Режимы HTTP `text`, `json_object`, `json_schema` и `llama_schema`
выбираются по возможностям маршрута. Для лимита генерации выберите
`max_tokens` или `max_completion_tokens`. При необходимости задайте
`reasoning_effort` и таблицу `headers_env` с именами переменных
окружения вместо значений заголовков. Для `openai` можно явно выбрать
`reasoning_format = "object"`: `none` отправляет `reasoning.enabled = false`,
а `low`, `medium` и `high` — `reasoning.effort`. Без этой настройки
отправляется обычный `reasoning_effort`. Поддержка параметров зависит
от поставщика: даже успешный ответ не доказывает отключение рассуждения
или соблюдение лимита генерации. Ошибка запроса сохраняется в попытке.
Уберите `temperature` из HTTP-профиля, если маршрут управляет этим параметром.
Секреты передаются только через HTTPS или loopback HTTP; удалённый
`llama_server` по HTTP допускается только без секретных заголовков и ключа.
Известные контакты скрываются во всех вхождениях, даже внутри слов: короткий
контакт может поэтому закрыть часть обычного текста.

Для прямого запуска задайте переменные в окружении процесса.
Compose применяет корневой `.env` при подстановке путей и обычных
переменных конфигурации. Для секретов Worker можно использовать
приватный `.env.llm` или указать отдельный файл через
`ANKETAPARSER_LLM_ENV_FILE`. Секреты, приватный TOML и GGUF исключены
из Git и контекста Docker. При смене профиля перезапустите Worker
контролируемо.

## Запуск и диагностика

Подготовьте совместимую схему [по руководству хранилища](persistence.md).
В обычном Compose работают сборщик и PostgreSQL. Worker включается
явно и использует ту же БД. Конфиг монтируется только для чтения.

```powershell
docker compose --profile llm up -d --build llm-worker
docker compose logs llm-worker
```

Для нативного режима укажите в TOML `gguf_path = "/models/model.gguf"`.
Задайте `ANKETAPARSER_LLM_GGUF` с путём к файлу на машине и подключите
[дополнение Compose](../compose.llm-native.yaml).

```powershell
docker compose -f compose.yaml -f compose.llm-native.yaml --profile llm up -d --build llm-worker
```

Пример прямого запуска из checkout после Release-сборки, настройки
изолированной БД и загрузки [корпуса](../tests/fixtures/llm/README.md).

```powershell
$cli = "src/AnketaParser.Cli/bin/Release/net10.0/AnketaParser.Cli.dll"
dotnet $cli llm config
dotnet $cli llm status
$revision = (dotnet $cli source post 210007 --fixture | ConvertFrom-Json).result.revisionId
dotnet $cli llm run $revision
dotnet $cli llm decision $revision
```

`source post` возвращает `result.revisionId`. Для фикстуры добавьте
`--fixture`. `llm run` захватывает одно доступное задание указанной
ревизии и возвращает `idle`, если сейчас захватывать нечего.
`llm worker` обрабатывает очередь до остановки процесса или
несовместимости с движком. Его журналы идут в stderr.
`llm config` проверяет параметры, наличие секретов и локального файла.
Доступность HTTP и работоспособность нативного backend подтверждаются
вызовом модели. В `llm status` показаны очередь, завершённые попытки,
категории отказов и фактически предоставленная статистика токенов.
Если TOML или профиль некорректны, `llm status` возвращает состояние
очереди и категорию `configurationFailure`.

Для проверки используйте отдельную мигрированную БД и
[обезличенный корпус](../tests/fixtures/llm/README.md).
`run` и `worker` меняют очередь, сохраняют результаты и могут расходовать
лимит выбранного маршрута. Обычные диагностические команды сборщика
работают при отсутствующем или неисправном LLM-профиле.

## Версии, повторные попытки и расходы

При первом захвате версия обработки закрепляется за заданием. Она
учитывает промты, схему, действующие настройки движка и модель.
Для локального GGUF учитывается SHA-256 файла. Для удалённых моделей
применяйте версионированный ID, если поставщик его предоставляет.

Смена профиля влияет на ещё не привязанные задания. Для уже
обрабатывавшейся ревизии явно выполните `llm reprocess <revision-id>`
с нужным профилем. Повтор команды возвращает существующее задание
этой версии. Для исчерпанных или окончательно остановленных заданий
той же версии используйте `--retry-failed` после устранения причин.
История попыток сохраняется. Устаревшую или исключённую ревизию
поставить в очередь нельзя.

Временные отказы и ошибки формы ответа, сочетания класса с причиной или
дословного подтверждения дают ограниченные повторы с задержкой; неверная
цитата не принимается. Свидетельство находится в подготовленном тексте
дословно либо отличается от него только регистром символов и длиной
пробельных серий: модель часто заменяет перенос строки пробелом, а
координаты фрагмента всё равно берутся из исходного текста. Маскированный
контакт (`█`) внутри фрагмента допустим, потому что значение уже обезличено;
фрагмент, состоящий только из маски, пунктуации и символов, не принимается
как подтверждение. Окончательный отказ по такой причине означает, что модель
исказила цитату словами или объединила несоседние строки: такое решение не
сохраняется как анализ. Каждая попытка расходует установленный бюджет
задания, а после исчерпания попыток оно получает состояние `failed`.
Проверенная классификация `profile` записывается в историю попытки до
извлечения полей; при повторе того же задания и совпадении хеша подготовленного
текста она используется повторно. `llm decision` показывает её в `checkpoints`:
это промежуточный результат, а не завершённый анализ или `Candidate`.
При изменении подготовленного текста классификация запрашивается заново.

При 429 учитывается `Retry-After` с пределом в сутки. После аварийной
остановки незавершённое задание становится доступным следующему
Worker по истечении аренды; длительность аренды покрывает два
настроенных таймаута и запас на работу с БД. Сбой Worker не
останавливает Host.

На попытку приходится до двух модельных вызовов. Опциональный
`daily_request_limit` ограничивает общий резерв HTTP-запросов в этой
БД за сутки UTC для маршрута и имени переменной ключа. Резерв
учитывается при захвате задания, включая случаи, когда второй вызов
не потребовался или Worker был прерван. `max_output_tokens`,
`max_input_chars` и `concurrency` также ограничивают нагрузку.
Статистика токенов сохраняется и для отвергнутых ответов, если провайдер
её прислал: обрыв по лимиту, отказ модели и непригодная форма ответа не
скрывают расход, но и не превращаются в успешный результат.
Стоимость зависит от тарифа маршрута и фактических токенов.
При обрыве связи после принятия запроса провайдером повтор может
оплачиваться отдельно.
