# Хранилище, миграции и резервирование

[Все руководства](README.md) · [Эксплуатация](operations.md)

## Модель и операции

Core/Persistence/IProductStore задаёт типизированные операции хранения,
Infrastructure реализует их через ProductStore и EF Core 10/Npgsql provider 10.
Контекст и миграции находятся в src/AnketaParser.Infrastructure/Persistence.
AddAnketaParserInfrastructure регистрирует scoped-контекст и хранилище.
Параллельным обработчикам нужны разные scopes; один контекст используют
последовательно, без оставленных внешним кодом незаписанных изменений.

| Сущности | Контракт |
| --- | --- |
| Source, OriginalPost | Уникальный номер поста внутри источника; повторное обнаружение обновляет LastSeenAt |
| PostRevision | Уникальная пара пост/SHA-256 содержимого; оригинал отделён от интерпретации; метаданные получения — jsonb |
| Analysis, Profile | Каждая обработка или ручная коррекция создаёт новую запись; Processor хранит происхождение, SchemaVersion — версию анализа |
| Contact, ContactObservation | Платформа и нормализованное значение обозначают контакт; наблюдения сохраняют написание, уверенность и provenance |
| TelegramAccount | Числовой технический ключ в схеме private; Id — отдельный случайный UUID |
| TelegramUsername, ContactVerification | История username и основания подтверждения; уникальность username действует только среди открытых интервалов |
| Anon, ProfileLink | Внутренняя группа предполагаемых связей; Suggested и VerifiedAccount не устанавливают личность или авторство |
| BotUser, BlacklistEntry | Пользователь бота отделён от аккаунта анкеты; уникальная пара OwnerId/AnonId, причина и дата; Settings — jsonb |
| Complaint, ModerationDecision | Жалобы принадлежат отправителям; решение содержит исполнителя, основание, действие и необязательное доказательство владения |
| ProcessingJob, JobAttempt | Уникальность версии обработки для ревизии; ограничение попыток, аренда, токен захвата и история отказов |

Нормализацию контакта выполняет вызывающий адаптер по правилам платформы.
Нельзя безусловно приводить всю почту к нижнему регистру. Контакты не сливают
людей. Несколько контактов одной платформы сохраняются раздельно.
ConfirmTelegramAsync принимает уже проверенный ID и доказательство, не обращается
в Telegram и не доказывает авторство. LinkAsync возвращает ProfileLinkResult
с LinkId конкретной связи и AnonId группы;
UnlinkAsync принимает LinkId. Повторная отмена сохраняет первоначальные
UnlinkedAt и UnlinkReason,
в том числе при конкурентных вызовах. Автоматического объединения групп
по контакту нет. Подтверждённая связь ссылается на конкретную ContactVerification;
разные проверенные аккаунты не объединяются в группе со статусом VerifiedAccount. Группировка по аккаунту оформляется явной связью с provenance.
ContactId и AccountId подтверждения неизменяемы на уровне БД; новое основание
сохраняется отдельной записью, чтобы не менять смысл существующих связей.

Наблюдения и оценки анализа находятся в разных jsonb-полях, известные признаки —
в отдельных nullable-колонках. NULL означает неизвестный факт, пустая строка —
явно переданное пустое значение. Не выводите возраст/пол из косвенных признаков.
Низкоуровневый контекст предназначен для доверенных внутренних компонентов;
аутентификацию будущего интерфейса он не заменяет. ReadBlacklistAsync и ReadSettingsAsync фильтруют данные по владельцу, SaveSettingsAsync
сохраняет настройки отдельно для каждого BotUser. RecordOwnershipCheckAsync пишет
результат проверки жалобы и доказательство без автоматического изменения публикации.
Владелец blacklist/жалобы
должен поступать из проверенной сессии будущего бота, а не из пользовательского ввода.

PublishAsync публикует анкету. LatestAsync выбирает последний опубликованный
неисключённый результат группы по времени создания результата и UUID.
Жалобы сами не меняют публикацию. ArchiveAsync атомарно исключает оригинальный
пост, архивирует его результаты и пишет решение. Это закрывает повторную публикацию
того же оригинала, включая новые обработки. Другие посты и аккаунты сохраняются.
Возврата из архива штатной операцией нет; удаление персональных данных требует
отдельной утверждённой политики. FK используют RESTRICT без каскадного удаления.

PostgreSQL обеспечивает диапазоны возраста/уверенности/состояний, уникальность,
происхождение анкеты и контакта, подтверждение для VerifiedAccount и необратимость
исключения. Импорт и регистрация идентичностей используют транзакционные advisory
locks, задания — FOR UPDATE SKIP LOCKED. Истёкший токен не может завершить
повторно захваченное задание. В CompleteAsync вызывающий код обязан передавать
безопасную категорию отказа без текста LLM, контактов, секретов и сообщений
исключений. Хранилище проверяет только длину категории и не очищает её содержимое;
задержка повторов ограничена 300 секундами.
Сохранение новых постов не зависит от успеха обработки.

ReviewAsync переводит Candidate или явно пересматриваемую Rejected в Reviewed,
RejectAsync отклоняет неархивную анкету. Обе операции требуют исполнителя и
основания, сохраняют ModerationDecision. Повторное отклонение идемпотентно.
PublishAsync сохраняет прямую публикацию Candidate/Reviewed, но отклонённую
анкету сначала требуется явно проверить повторно. Архив и исключение оригинала
не снимаются этими операциями. Жалобы сами по себе не меняют публикацию.

## Новая БД и переход существующей установки

Обычный docker compose up не применяет миграции. Задайте три разных пароля
в исключённом из Git .env: PRODUCT_RUNTIME_PASSWORD, PRODUCT_MIGRATION_PASSWORD,
PRODUCT_BACKUP_PASSWORD. POSTGRES_USER/PASSWORD сохраняют исходную
инициализационную учётную запись. На существующем томе изменение переменной
POSTGRES_PASSWORD не меняет серверный пароль.

Перед обслуживанием существующей установки согласуйте остановку записи,
создайте административный pg_dump -Fc и подтвердите восстановление в отдельной БД.
Агент не выполняет эти действия с рабочей базой без отдельного разрешения.
Не меняйте имя проекта, postgres-data или PGDATA. Provisioning работает
на запущенном кластере и не зависит от entrypoint init-скриптов.

    docker compose up -d --wait postgres
    docker compose build host maintenance

Передайте существующую административную строку подключения через временную
переменную окружения ANKETAPARSER_Database__ConnectionString. Не помещайте её
значение в команду, историю оболочки или журнал. Затем:

    docker compose run --rm -e ANKETAPARSER_Database__ConnectionString maintenance storage provision
    docker compose run --rm maintenance storage migrate
    docker compose run --rm maintenance storage schema
    docker compose up -d --wait host backup

Удалите административную переменную после provision. Provisioning повторяемо
создаёт роли, проверяет отсутствие высоких атрибутов/членств, задаёт пароли,
создаёт схемы и grants/default privileges. Существующие данные не удаляет.
Чужие схемы/объекты автоматически не присваивает: конфликт ownership требует
ручного разбора. Runtime имеет DML в product/private, мигратор владеет
прикладными схемами, backup имеет SELECT. Ни одна служебная роль не получает
SUPERUSER/CREATEDB/CREATEROLE. Секреты pg_authid недоступны runtime.
Административный пароль не передаётся Host или backup.
Доступ к private нужен доверенному backend для работы с аккаунтами; публичная
выдача PublicProfile числовых Telegram ID не содержит. Это разделение сервисных
полномочий, а не отдельная роль PostgreSQL каждого конечного пользователя.

Миграции транзакционны; повторное применение не дублирует данные.
Неизвестная более новая миграция блокирует применение и готовность.
Применение отделено от Host. Перед разрушающей миграцией нужны анализ DDL,
backup и проверенное восстановление. Down не возвращает потерянные данные.

    dotnet tool restore
    dotnet ef migrations add <Имя> --project src/AnketaParser.Infrastructure --output-dir Persistence/Migrations
    dotnet ef migrations script --idempotent --project src/AnketaParser.Infrastructure --output .codex/local/migrations.sql
    dotnet ef migrations has-pending-model-changes --project src/AnketaParser.Infrastructure

Design-time factory строит модель без секрета. Применённые миграции не редактируют,
добавляют новые. SQL триггеров находится в миграции StorageGuards.

## Резервирование

Сервис backup запускает storage backup-daemon сразу и далее с интервалом.
Использует утилиты PostgreSQL 18, custom-архив, отдельный том backups и роль
product_backup. Host монтирует том только для чтения. Файлы 0600 и каталог 0700
доступны владельцу UID 1654 (пользователь стандартных .NET-образов).
При прямом запуске на Windows оператор ограничивает ACL каталога учётной записью
обслуживания; Unix mode там неприменим.

| Backup-настройка | Значение по умолчанию |
| --- | --- |
| Directory | Обязательна для включения; Compose: /backups |
| ConnectionString | Отдельная строка backup-роли |
| IntervalSeconds / TimeoutSeconds | 86400 / 1800 |
| Daily / Weekly / Monthly | 7 / 4 / 3 разных календарных корзин; совпадения объединяются |
| MaxBytes | 10737418240 байт опубликованных архивов |
| RestoreJobs | 1: транзакция; 2–16: параллельное восстановление с возможным частичным результатом при отказе |
| ExternalDirectory | Не задан; необязательный независимый каталог |
| PgDump / PgRestore | pg_dump / pg_restore из PATH |

Настройки доступны через общий порядок загрузки JSON и переменных окружения, например
ANKETAPARSER_Backup__TimeoutSeconds. В Compose дополнительные параметры
задаются явно в секции environment. Интервал и MaxBytes вынесены
в BACKUP_INTERVAL_SECONDS/BACKUP_MAX_BYTES. Один процесс делает один дамп;
конкурирующий запуск отклоняет файловая блокировка. Custom pg_dump не поддерживает
параллельную выгрузку; RestoreJobs управляет только восстановлением.
TimeoutSeconds ограничивает всю попытку backup: запросы, PostgreSQL-утилиты,
хеширование и асинхронное внешнее копирование. Для отдельных backup-verify и
restore-empty этот параметр ограничивает каждый запуск утилиты, а не всё
восстановление. Ctrl+C и SIGTERM в контейнере отменяют daemon во время работы
и ожидания; status.json различает cancelled и timeout. Отмена перед публикацией
сохраняет предыдущий успех, после публикации — новый. Синхронные операции
файловых метаданных и зависший ввод-вывод ядра не имеют гарантированного срока
отмены: сетевому носителю нужны собственные системные ограничения ожидания.

Архив публикуется после успеха pg_dump, чтения оглавления и всех блоков
через pg_restore; сохраняется SHA-256. Partial-файл не считается копией.
Это структурная проверка, а не доказательство восстановления.
Сначала подготавливаются архив и сумма, затем публикуется имя .dump; status.json
атомарно заменяется после готовности локальной и настроенной внешней копий.
Отказ до фиксации состояния удаляет только файлы этой попытки; прежняя копия
сохраняется. Отказ ротации после публикации записывается как rotation_failed
без отката LastSuccess/Archive. Аварийное выключение между переименованиями
может оставить неучтённые файлы; они не доказывают успешное резервирование.
Ротация после успеха сохраняет последнюю успешную и копии с отметкой
полного восстановления. Если защищённые копии не помещаются, операция сообщает
отказ и требует переноса/увеличения лимита. Для временного дампа нужно
дополнительное свободное место размером одной копии. Лимит относится к архивам,
не к метаданным и внешнему хранилищу. Сторонние файлы/partial после аварии
автоматически не удаляются: перед очисткой установите происхождение.
Дамп включает схемы product/private и определения public с историей
public.__EFMigrationsHistory. Остальные таблицы, представления и последовательности
public исключаются по каталогу; другие схемы и большие объекты не копируются.
Чужие строки не читаются, дополнительные права SELECT не нужны. Определения
функций и типов public могут входить как зависимости; это не копия всей БД.
Независимые данные требуют отдельного административного резервирования.
Во время обслуживания не меняйте состав объектов DDL параллельно с выгрузкой.

Подключения pg_dump/pg_restore получают режим TLS, CA, клиентский сертификат/ключ,
режим согласования TLS, GSS и channel binding из строки подключения. Проверка
отзыва сертификата средствами .NET и пароль TLS-ключа не имеют поддерживаемого
переноса через окружение libpq: при таких настройках операция отклоняется.
Унаследованные параметры подключения PG* очищаются перед явной настройкой;
локализация и параметры сеанса, не меняющие подключение, сохраняются.
Приоритет переменных описан в [документации libpq](https://www.postgresql.org/docs/18/libpq-envars.html).

    docker compose run --rm maintenance storage backup
    docker compose run --rm maintenance storage backup-status
    docker compose run --rm maintenance storage backup-list
    docker compose run --rm maintenance storage backup-verify <имя.dump>
    docker compose run --rm maintenance storage backup-rotate

Статус содержит последний успех/отказ, безопасную категорию и последнюю
проверку восстановлением. Doctor сохраняет прежнюю схему JSON, добавляя пробу
backup при настроенном каталоге. Нет копий, последний отказ новее успеха,
возраст больше двух интервалов или нет свежей проверки восстановлением —
degraded. Проверяются доступность и размер текущего архива, его SHA-256 в
метаданных и совпадение отметки восстановления с именем, размером и суммой.
На healthcheck файл целиком не хешируется и восстановление не выполняется.
Изменения того же размера обнаруживает backup-verify, а не проверка метаданных.
После нового backup требуется новое подтверждение восстановлением именно этой
копии; старые отметки без привязки не дают healthy. Неготовая схема БД — unhealthy и код 4.

Отдельный том на том же диске не защищает от отказа диска. Для независимой копии
смонтируйте внешний каталог в maintenance/backup и задайте ExternalDirectory:
сервис копирует архив атомарно с проверкой суммы. Ротацию внешнего назначения
задаёт оператор отдельно. Без настроенного назначения независимой копии нет.
Используйте шифрование носителя и защищённый транспорт (например SSH/SFTP)
с отдельным хранением ключей; собственного шифрования архивов приложение
не реализует. Архивы содержат персональные данные.

## Восстановление и точность

При необходимости подготовьте роли provisioning через отдельную служебную БД
на целевом экземпляре. Затем создайте другую пустую БД под владельцем
product_migrator. До восстановления не выполняйте provisioning в целевой БД:
он создаёт схемы product/private, которые конфликтуют со схемами из архива.
Дайте владельцу CREATE на целевую БД. Миграции заранее не применяйте:
схема и история поступают из архива. Задайте Restore:ConnectionString через
защищённую переменную окружения и пропустите её в контейнер:

    docker compose run --rm -e ANKETAPARSER_Restore__ConnectionString maintenance storage restore-empty <имя.dump>

Команда проверяет SHA-256, отказывается от исходной БД (сервер, порт и имя) или непустой цели,
выполняет pg_restore без clean/owner/ACL и проверяет версию схемы.
После успеха ставит отдельную отметку проверки восстановлением конкретного архива.
Предвалидация отклоняет даже пустые пользовательские схемы, типы и функции до
запуска pg_restore; одна пустая public допустима. Повторное восстановление
в заполненную цель отклоняется без очистки. BackupRecoveryTests
сравнивает выбранные записи синтетической БД: исходные записи, связи,
технический аккаунт, архив и историю миграций. Это не доказывает эквивалентность
данных конкретного рабочего архива: восстановленные рабочие данные требуют
отдельного сравнения с источником и проверки полноты и связности.
Роли/пароли не входят в дамп; provisioning и grants нужно воспроизвести отдельно
до допуска приложения к восстановленной БД.

Рабочее восстановление автоматически не выполняется. Для него нужны отдельное
разрешение с точной целью, сохранение текущих данных, остановка записи,
восстановление в новую БД, проверка связей/прав/версии и контролируемое переключение.
Сверьте решения модерации после точки копии перед допуском выдачи: старый архив
может вернуть исключённый материал. Restore-empty эту сверку не выполняет.

Pg_dump даёт согласованный снимок на начало выгрузки. При ежедневном интервале
возможна потеря изменений примерно за сутки плюс задержки/отказы; RPO/RTO
владельцем не утверждены. WAL/PITR и почасовой откат не реализованы.
Время восстановления зависит от объёма, носителя и проверок; синтетический тест
не устанавливает боевой RTO.

Совместимость: [Npgsql EF Core 10](https://www.npgsql.org/efcore/release-notes/10.0.html).
Раздельные миграции: [EF Core](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying).
Логические архивы: [PostgreSQL 18](https://www.postgresql.org/docs/18/app-pgdump.html).
