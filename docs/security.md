# Безопасность и ограничения

[Все руководства](README.md) · [Эксплуатация](operations.md)

Хранилище поддерживает анкеты, контакты, аккаунты, персональные списки, жалобы,
очередь и миграции. Это не готовый сервис сбора и публикации: парсер, Telegram,
LLM, подписки, уведомления, HTTP API и административный веб-интерфейс не реализованы.
Права, архивы и восстановление описаны в [регламенте хранения](persistence.md).
Карта компонентов — в [архитектуре](architecture.md).

## Секреты и диагностические данные

Строку подключения храните в переменной окружения либо игнорируемом локальном
файле; `.env` и `appsettings.Local.json` не должны попадать в коммит.
Публичный `.env.example` содержит заменяемые примеры. Пароль-заглушка Compose
предназначен для локальной воспроизводимости; задайте свой пароль.
`.codex/context/` публичен; личные настройки, промпты, описания PR, кеши и состояние
инструментов остаются в игнорируемых каталогах.

[ConnectionStringDescriptor](../src/AnketaParser.Infrastructure/Configuration/ConnectionStringDescriptor.cs)
представляет адрес как `host:port/database`, без имени пользователя и пароля.
Валидаторы не повторяют сырую строку подключения. `DiagnosticsRunner` заменяет
текст исключения пробы именем типа; результат пробы PostgreSQL использует
классификацию ошибки. В JSON есть сведения о машине, процессе и адресе БД:
их также нужно просматривать перед публикацией.

`PostgresReadinessProbe` записывает событие `2001` с безопасным адресом и категорией
отказа, без объекта исключения. Ошибки чтения JSON и привязки настроек заменяются
безопасными сообщениями без исходных значений. Общие обработчики Host и CLI
выводят только тип неожиданного исключения, без `Message`, стека и вложенных причин.
`ConnectionStringDescriptor.Redact` разбирает только строки подключения и не
предназначен для фильтрации произвольного текста исключения. Не выводите сырую
конфигурацию; сведения о машине и адресе БД проверяйте перед публикацией.

## GitHub Actions

Обычный CI исполняет код PR с `contents: read`, без дополнительных секретов;
checkout не сохраняет учётные данные. Линтеры работают в отдельном задании на тех же
непривилегированных событиях, включая PR из форков. Установка проверяет закреплённые
SHA256 официальных бинарных архивов до исполнения; zizmor не получает токен и
работает без сети. Команды и ограничения проверки приведены в
[руководстве разработки](development.md).

В [доверенном workflow](../.github/workflows/pr-body-trusted.yml) намеренно
сохранён `pull_request_target`: он получает валидатор из точного
`github.event.pull_request.base.sha`, а не из head. Единственное исключение в строке
`dangerous-triggers` относится к этому событию: checkout не сохраняет учётные
данные, права доступа ограничены `contents: read` и `pull-requests: read`, номер PR
поступает через `env`, команда запуска литеральна. Python-модули валидатора берутся
из base; подмена модулей head проверяется регрессионным тестом
[test_trusted_pr_validation.py](../.github/scripts/test_trusted_pr_validation.py).
Исключение требует повторной оценки при изменении ref, команды, импортов,
окружения или прав доступа. Оно не распространяется на другие workflow или правила.

Кандидатная проверка `pull_request` исполняет код PR и не обеспечивает
независимого контроля. Статический аудит не заменяет проверку границ доверия и
не защищает от всех изменений workflow, которые может предложить автор PR.
Настройка обязательных проверок выполняется отдельно после проверки реально
активных контекстов.

## Секреты в истории Git

[Рабочий процесс секретов](../.github/workflows/gitleaks.yml) проверяет новые
коммиты закреплённым Gitleaks `8.30.1` из официального GitHub Release: архив
скачивается по HTTPS и сверяется по SHA256 до распаковки. Проверка выполняется
на `pull_request`, push в `main` и `merge_group`.

[check_gitleaks.py](../.github/scripts/check_gitleaks.py) разрешает диапазон по
событию: для PR — коммиты `base..head`, для push — весь `before..after`, поэтому
промежуточные коммиты не теряются, а для нового ref — вся достижимая история.
Неглубокий клон, отсутствующий коммит и недостающие объекты диапазона означают
недоказанный охват и блокируют проверку. Если старый tip исчез после перезаписи
истории push, проверка явно переходит к полному аудиту истории нового tip.

Диффы слияний входят в проверку (`--diff-merges=on`): правка, внесённая только
при разрешении конфликта, тоже обнаруживается. Сканирование запрашивает
текстовые диффы (`--text`), поэтому атрибут `-diff` в `.gitattributes` не
скрывает содержимое файла от проверки. Значения скрывает сам инструмент
(`--redact=100`), а отчёт содержит только правило, путь, строку и коммит.
Значения секретов не публикуются ни при успехе, ни при блокировке.

Найденный секрет требует отзыва или ротации владельцем: проверка историю не
переписывает и не удаляет. Базовый список исключений и широкие разрешающие списки не используются;
допустимое исключение должно быть точечным и проверяемым.

## Уязвимости зависимостей

Политика аудита задана в [Directory.Build.props](../Directory.Build.props):
`NuGetAudit=true`, `NuGetAuditMode=all`, `NuGetAuditLevel=low`. Проверяются прямые
и транзитивные пакеты, поэтому известный advisory транзитивной зависимости не
остаётся незамеченным: в режиме `direct` он не обнаруживается. Строгая сборка
превращает предупреждения NU190x в ошибку, поэтому недоступный источник данных об
уязвимостях или найденный advisory останавливают восстановление.
[NuGet.config](../NuGet.config) задаёт явный `auditSources` с официальным
адресом сервиса уязвимостей, чтобы отсутствие данных об уязвимостях не выглядело
успешным аудитом; пакеты по-прежнему загружаются только из `nuget.org`.

[Аудит уязвимостей](../.github/workflows/dependency-audit.yml) выполняет два
независимых задания. Первое восстанавливает решение с закреплёнными версиями и перечисляет
бюллетени уязвимостей; [check_nuget_audit.py](../.github/scripts/check_nuget_audit.py)
доказывает, что проверены все проекты решения и запрошен транзитивный режим.
Непустой раздел `problems` отчёта блокирует проверку: предупреждение о недоступных
данных об уязвимостях не доказывает аудит.
Второе запускает закреплённый OSV-Scanner с проверкой SHA256 и проверяет каждый
отслеживаемый `packages.lock.json` и файл требований отдельно. Флаг
`--all-packages` включает в JSON пакеты без уязвимостей. Проверка сверяет источник,
экосистему, нормализованное имя и точную версию каждого пакета с независимым
инвентарём манифеста. Пропущенная/лишняя запись, неверная версия, повреждённый
отчёт, неразобранный формат и сбой API блокируют проверку. Только ссылки с типом
`Project` в исходном lock-файле исключаются из аудита пакетов; сканер может
показывать их без версии. Код `0` сам по себе полноту охвата не доказывает.
Код `128` допускается только для заведомо пустого источника; пустой общий
инвентарь блокируется. Отсутствие уязвимостей сообщается после сверки охвата.

Границы этой проверки: файл требований с точными версиями описывает только
объявленные зависимости и не доказывает полный разрешённый граф Python; OSV по
манифестам не является аудитом пакетов операционной системы в образах, версий SDK
и внешних бинарников. Существующее дерево зависимостей проверяют NuGet Audit и
OSV, а изменения зависимостей в PR — отдельная проверка Dependency Review.

## Изменения зависимостей в pull request

[Проверка зависимостей](../.github/workflows/dependency-review.yml) запускается
только на непривилегированном `pull_request` и анализирует зависимости, которые
PR добавляет или обновляет. Action закреплён полным SHA проверенного выпуска,
получает только `contents: read` и штатный токен без дополнительных секретов, не
публикует комментарии и не изменяет репозиторий. Блокируются уязвимости любого
опубликованного уровня серьёзности во всех областях зависимости; лицензионная политика не
вводится, режим `warn-only` не используется.

Порог задаётся `fail-on-severity` и `fail-on-scopes`; при отказе API, отсутствии
снимков графа или недостаточных правах задание падает, а не сообщает об успехе.
Отдельный шаг сверяет отчёт действия с изменениями, посчитанными из самих
манифестов между base и head. Идентичность включает вид изменения, путь файла,
экосистему, имя и точную версию. Замена версии требует двух записей API:
`removed` для старой и `added` для новой. Совпадение в другом файле или с другой
версией не подтверждает охват; диапазон вместо разрешённой версии также
блокирует проверку. Отсутствие изменений проходит только при пустом отчёте:
изменение, которое действие обнаружило, но которое не выведено из манифестов,
считается пробелом охвата, а не успехом. Обратное расхождение проверяется так же:
запись отчёта вне разобранных манифестов блокирует сверку, кроме экосистемы
Actions, которая подтверждается отдельно.

Вывод `dependency-changes` передаётся в проверку через переменную окружения шага:
политика zizmor для этих рабочих процессов запрещает интерполяцию вывода в текст
скрипта (`template-injection`). Если отчёт превысит предел длины строки
окружения, шаг завершится отказом, но не подтвердит охват.

Границы: этот workflow оценивает только изменения PR, существующее дерево
проверяют задания аудита уязвимостей. GitHub Dependency Graph возвращает для
части NuGet-зависимостей диапазон вместо разрешённой версии, поэтому такие записи
не доказывают анализ конкретной версии и отмечаются как пробел, а не как успех.
Ссылки GitHub Actions на SHA перечисляются как неподтверждённые даже при
наличии записи в графе: наличие зависимости не доказывает аудит её закреплённого
кода. GitHub поддерживает предупреждения об уязвимостях Actions для семантических
версий, а не SHA; снимок PR также может не содержать часть новых ссылок.
[Поддерживаемые форматы графа](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems)
не включают NuGet lock-файлы и центральный файл версий: без точного подтверждения
по источнику сверка блокируется, а анализ других файлов за него не выдаётся.
Проверки NuGet Audit и OSV отдельно проверяют разрешённые пакеты.

Флаг полного инвентаря OSV закреплён в
[контракте OSV-Scanner 2.7.1](https://github.com/google/osv-scanner/blob/v2.7.1/cmd/osv-scanner/internal/helper/flags.go),
а форма `added`/`removed` и поля источника/версии — в
[ChangeSchema закреплённого Dependency Review](https://github.com/actions/dependency-review-action/blob/a1d282b36b6f3519aa1f3fc636f609c47dddb294/src/schemas.ts).

Аудит lock-файлов запускает OSV-Scanner с `--all-packages` и `--no-resolve`:
разрешение транзитивных зависимостей манифеста выключено, поэтому отчёт
доказывает ровно объявленный инвентарь, а лишний пакет в отчёте остаётся
пробелом охвата. Ссылки `Project` в lock-файле пакетами не считаются.

## Контейнеры и данные

Основной Compose не публикует порты, но сеть `backend` не помечена `internal`:
это не обещание полной сетевой изоляции. Отладочный файл публикует PostgreSQL
только на петлевом интерфейсе. Host запускается без root с `no-new-privileges`; это
не заменяет контроль доступа к Docker на машине.

[Dockerfile](../Dockerfile) копирует проектные файлы и `src/`, а
[.dockerignore](../.dockerignore) исключает локальные файлы окружения и переопределения
из контекста сборки на любой глубине (`**/.env`, `**/.env.*`,
`**/appsettings.Local.json`). Не помещайте секреты в произвольные файлы `src/`:
они могут попасть в контекст. Успех `SELECT 1` не подтверждает шифрование,
резервное копирование или корректность прикладных данных.

Именованный том PostgreSQL хранит данные независимо от контейнера. Удаление
тома разрушает данные; безопасная остановка и предупреждение для
`down --volumes` находятся в [эксплуатации](operations.md). Изменение исходников
не разрешает перезапуск рабочей среды, миграцию или удаление данных. Проверка Docker
использует собственный стек и синтетическую БД, а не рабочий том.

Если обнаружен дефект обработки исключений или утечка, зафиксируйте место и
наблюдаемый эффект отдельно. Документация описывает существующее поведение;
менять исполняемый код ради соответствия тексту нельзя.
